Technical Requirements

15. Form Validation

⚠️ AT RISK

A "Yes" is possible but depends on a fix or on how the evaluator reads it. · audited 2026-09-18 · branch main @ 2143958

The architecture is right — one set of Zod schemas in packages/schemas validates in TanStack Form on the client and in every tRPC procedure on the server; injection and XSS are handled by Drizzle and React. But the event schema is loose enough that a hand-crafted request produces a 500 that leaks SQL.

What the evaluator is asked

Are all forms and user inputs validated in both frontend AND backend?

  • Test with invalid inputs (empty fields, wrong formats, SQL injection attempts, XSS attempts, etc.).
  • Both client-side and server-side validation must be present. Server-side validation is critical for security.

Red flags

highEvent date/time accepted as free text on the server

Fix in createEventSchema: date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/), time: z.string().regex(/^\d{2}:\d{2}$/), plus a .refine that toEventDateTime(date, time) is a valid, future date. Five lines, both sides get it for free.

highNo maximum lengths on event text fields, no capacity ceiling

title max(120), location/address max(200), description max(5000), maxCapacity max(100000). Same file.

mediumImage validated only in the browser

Add to the schema: image: z.string().startsWith('data:image/').max(MAX_EVENT_IMAGE_BYTES * 1.4) (base64 overhead) and the same for avatar in updateUserSchema. The constants already exist in events.ts.

mediumDatabase errors are sent to the client verbatim

Drizzle's Failed query: select … from "events" … reaches the browser as the tRPC error message (Q7 shows one). Add an errorFormatter/onError in the tRPC setup that replaces INTERNAL_SERVER_ERROR messages with a generic one in production.

What the code shows

Both sides, same schema

  • Client: CreateAccountForm, LoginForm, ForgotPasswordForm, ResetPasswordForm, EventForm import signUpSchema, signInSchema, … from @repo/schemas/auth / events into TanStack Form validators; errors render per field.
  • Server: every @Mutation/@Query in apps/backend/src/**/*.router.ts declares input: someSchema; nestjs-trpc rejects non-conforming input with BAD_REQUEST before the handler runs. better-auth validates its own signup/login bodies.
  • Authorization is also server-side: ProtectedMiddleware, AdminMiddleware, ownership check in events.router.ts assertCanManage, self-or-admin check in users.router.ts updateUser.

Injection and XSS

  • SQL injection: all queries go through Drizzle's query builder (parameterised). The single raw sql`…` (drizzle-event-listings.repository.ts getCategoryCount) has no user input in it. Typing ' OR 1=1 -- into any field stores it as text.
  • XSS: React escapes all interpolated text; there is no dangerouslySetInnerHTML or innerHTML anywhere in apps/frontend/src. Typing <script>alert(1)</script> as an event title displays it literally. E-mails are built with react-email components, which also escape.
