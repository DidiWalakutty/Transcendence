General Requirements

7. Deployment

❌ FAIL as-is

On main right now this gets a "No". Fix before Saturday. · audited 2026-09-18 · branch main @ 2143958

On a fresh clone the single command starts every container — and the app is broken, because nothing creates the database tables. Verified by running the built backend image against an empty PostgreSQL. It only works on your laptops because your postgres_data volume already has the tables.

What the evaluator is asked

Can the entire application be deployed with a containerization solution (Docker, Podman, etc.) using a single command?

  • Ask a team member to demonstrate the deployment.
  • The deployment should be straightforward and work without manual intervention.
  • Verify that all services start correctly and the application is accessible.

Red flags

criticalFresh clone + single command = broken app (no migrations in the deploy path)

The sheet says "check that git clone is used in an empty folder". An evaluator following that instruction gets a 500 on every page. This is the "Crash" flag. Fix is small; see below.

highNo seed → no admin user on a fresh deploy

The admin dashboard, role management and the "multi-user" demo need accounts. Either seed automatically or document one extra command and accept the risk.

mediumDocumented command needs a non-standard tool

README says vp run deploy. vp is Vite+, which the evaluator will not have. Document docker compose up --build as the single command (it is what vp run deploy runs anyway).

lowError responses leak SQL

The tRPC error above ships the full SELECT to the browser. Not a deploy problem, but an evaluator watching the network tab sees your table and column names. See Q15.

What the code shows

The experiment (reproducible)

Built image ft_transcendence-backend:latest + a brand-new postgres:17-alpine + redis:8-alpine on a throw-away network, then the first query the home page makes:

GET /api/trpc/events.getFeaturedEvents
→ {"error":{"json":{"message":"Failed query: select \"events\".\"id\", … from \"events\" left join \"registrations\" …",
   "code":-32603,"data":{"code":"INTERNAL_SERVER_ERROR" …

PostgreSQL has no events table because no migration ever ran. Every page that touches the database fails the same way; signup fails too (no users table).

Why nothing runs the migrations

  • vite.config.ts → repo:deploy is exactly docker compose up --build; no dependsOn, no migrate step. (repo:dev and repo:db:setup do migrate — that is why development works.)
  • docker-compose.yml has no migration service and no command override on backend.
  • apps/backend/Dockerfile copies only dist/, package.json, packages/ and production node_modules. Inside the image: apps/backend/drizzle/ does not exist and drizzle-kit is not installed (it is a devDependency). So even a manual docker exec … drizzle-kit migrate is impossible.
  • apps/backend/src/database/database.service.ts opens a pool and never calls migrate().
  • Your live stack has 8 tables — created weeks ago by vp run db:setup on the host and persisted in the ft_transcendence_postgres_data volume.

Second gap: no data, no admin

Nothing seeds. A fresh deploy has zero users, so the admin account (admin@transcendence.local, created only by apps/backend/seed.ts) does not exist and the admin dashboard / role-management module cannot be demonstrated. Seeding needs vp run db:seed on the host, which needs Vite+ and Bun installed — that is "manual intervention".

What does work

  • All six services build and start; postgres/redis have healthchecks; backend waits for them.
  • The stack is reachable at https://localhost:3000 through Caddy; HTTP redirects to HTTPS.
  • Rootless-Docker-friendly ports (3000/3080 instead of 443/80) with a comment explaining why.

Fix before Saturday

  1. Run migrations on backend startup (Drizzle ships a migrator in drizzle-orm, which is in production deps — no drizzle-kit needed): 
    // database.service.ts
import { migrate } from 'drizzle-orm/node-postgres/migrator';
async onModuleInit() {
  await migrate(this.client, { migrationsFolder: resolve(__dirname, '../../drizzle') });
}
    and in apps/backend/Dockerfile (runner stage) add COPY --from=builder /app/apps/backend/drizzle ./apps/backend/drizzle. Migrations are idempotent (Drizzle records applied ones in __drizzle_migrations), so restarts are safe.
  2. Alternative if you prefer not to touch the service: a one-shot migrate service in docker-compose.yml built from the builder stage (target: builder, command: bun x drizzle-kit migrate --config apps/backend/drizzle.config.ts) with backend.depends_on.migrate.condition: service_completed_successfully.
  3. Seed: simplest is a seed one-shot service (same builder image, command: bun apps/backend/seed.ts, depends on migrate) — the script is already idempotent. Or add SEED_ON_START=true handling in the backend. At minimum document the manual step and rehearse it.
  4. Then prove it: docker compose down -v (deletes the volumes!) → git clone into an empty folder → docker compose up --build → open https://localhost:3000 → sign up → see events. Do this on Friday on a machine that has never run the project.
  5. README §9: state docker compose up --build as the command; keep vp run deploy as an alias.

In the room: what to show and say

Demo from an empty folder, terminal visible: git clone … && cd ft_transcendence && docker compose up --build. While it builds, explain Caddy → frontend/backend → Postgres/Redis and the rootless-Docker port choice.
If asked "what runs the migrations?" — after the fix: "the backend applies pending Drizzle migrations at startup; the SQL lives in apps/backend/drizzle, generated from packages/schemas/src/database.ts."
