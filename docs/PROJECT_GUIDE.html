01 / Start with the product

What are we building?

ft_transcendence is an event platform. An organizer can publish an event, and other people can discover it, read its details, and connect with people they know.

Imagine Maya organizing a board-game evening. She creates an account, enters the location and date, chooses a category, and publishes the event. Leo opens the website to browse. He sees Maya's event and opens its detail page. If Maya changes the description, an open page that subscribes to event updates can receive that change without a manual refresh.

This guide explains the code on the docs-onboarding branch. It separates behavior present in the code from work that is only partly connected. It is a reading guide, not a claim that every feature has passed a live end-to-end test.

Area What exists in this branch
Events Browse and sort events, view details, create an event, and edit or delete events you own. Administrators can also manage events.
Accounts Sign up, log in, manage a profile, and enable two-factor authentication. Better Auth handles account and session machinery.
Friends and presence Send and manage friend requests. Presence tracks whether a user has an active connection to this backend process.
Live event updates Event changes travel to subscribed browsers. The frontend also detects an unresponsive event stream.
Registration and tickets The database table and persistence operations exist, but the registration router and service are empty. A complete ticket-booking flow is still unfinished.
Email and languages Welcome-email code exists, with limited signup integration. The website config enables English and Dutch. These details are explained below.
You do not need to memorize the tool names. First learn which job each part performs. Return to the tool table and glossary when a name is unfamiliar.
02 / The web in plain language

What happens when you open a website?

A browser is the program you use to visit websites. It asks another program for a page. That other program is a server: software that waits for requests and sends responses. During development, the browser and servers can all run on your own computer.

An address such as http://localhost:3000/events tells the browser where to go. localhost means this computer. 3000 is a port, a number that identifies which listening program should receive the request. /events is the path that identifies the page.

HTML gives the page structure

HTML describes headings, paragraphs, links, forms, and buttons. This guide itself is an HTML document.

CSS controls its appearance

CSS describes color, spacing, typography, and layout. A narrow phone screen can use a different layout from a desktop.

JavaScript adds behavior

JavaScript responds to clicks, submits forms, requests data, and changes what the browser displays.

TypeScript helps the developers

Most application code here is TypeScript. It adds checks about data types while developers work. Build tools turn it into JavaScript that can run.

HTTP is the set of rules the browser and server use to exchange requests and responses. HTTPS adds encryption in transit. A response can contain a page, an image, or structured data such as an event title and date.

Structured data often travels as JSON, a text format with named values. For example, {"title": "Board-game evening", "maxCapacity": 20} carries two pieces of information. It does not describe how to draw the event card.

A page appearing in your browser does not mean its data has been saved. A change becomes durable only when the backend successfully writes it to the database.
03 / The whole system

The project has three places where work happens

The word frontend means the part responsible for presenting the website. In this project, frontend code runs both in the browser and on a frontend server. The backend is a separate application that handles data requests and permissions.

The normal development addresses are localhost:3000 for the frontend and localhost:3001 for the backend. The user visits the frontend; the frontend sends data requests to the backend.

Another important piece does not run as its own server: packages/schemas. It contains definitions that both applications import. Those definitions describe the structure of users, events, and other data.

04 / Frontend

How a page gets its content

React lets developers describe a screen as smaller reusable pieces called components. An event card is one component; a navigation bar is another. A component takes information and describes what the screen should show. When that information changes, React updates the relevant display.

TanStack Router matches a URL to a page. In this repository, files inside apps/frontend/src/routes define the routes. The route /events/$eventId has a changing part: the ID selects which event to load. A route can also check the session before showing a protected page.

  1. First visit: prepare the page

    TanStack Start runs page preparation on the frontend server. The root route reads the session, and page loaders request important data from the backend. A loader is code that gets data ready for a page.

  2. Send useful HTML

    The frontend server builds HTML from that data and sends it to the browser. This is server-side rendering, often shortened to SSR. The visitor can receive meaningful page content in the first document.

  3. Make the page interactive

    The browser loads JavaScript and connects behavior to the server-rendered page. This step is called hydration. The fetched data also transfers into the browser's query cache.

  4. Handle later interactions

    Forms, navigation, and subscriptions run in the browser. React updates the view as data changes. Some navigations can reuse already loaded information.

Remembering results with TanStack Query

A cache is a saved copy that avoids repeating work. TanStack Query keeps a frontend cache of data fetched from the backend. It also tracks whether a request is waiting, succeeded, or failed. A query key identifies an entry, such as an event list with a particular sort order.

When data changes, code can replace the cached copy or mark it outdated so it will be fetched again. That second action is called invalidation. The cache is useful, but the database remains the durable record. A cache can be stale.

Forms and appearance

TanStack Form manages values and validation in several forms, including authentication forms. The event forms currently collect values more directly using the browser's FormData facility. Tailwind CSS controls layout and styling. The local components/ui folder provides reusable controls such as inputs, dialogs, and buttons.

05 / Requests and shared rules

How the frontend asks for data

An API is the set of operations one program makes available to another. Here, the backend offers operations such as reading events and creating an event. tRPC connects those operations to a TypeScript client in the frontend.

The frontend call can look like a normal function call in code, but it crosses the network. It can be slow or fail. The frontend must still handle loading states, errors, and lost connections.

Kind of operation Meaning Project example
Query Ask for existing information. Get the events organized by the logged-in user.
Mutation Ask to change information. Create an event, change its title, or delete it.
Subscription Keep receiving messages after the initial connection. Listen for event changes and update an open page.

Types and validation solve different problems

A type tells developers what a value should look like. For example, capacity should be a number. TypeScript can catch many mismatched values before the application runs. Those development checks do not prove that a request from the internet is valid.

Zod checks actual values while the application runs. A schema is a description of acceptable data. The event creation schema requires a nonempty title and a positive whole-number capacity. The backend validates input because a person can send a request without using our form.

The shared package contains both database table definitions and request/response schemas. Some schemas, such as user schemas, are derived from database definitions with drizzle-zod. Event request schemas are written separately. Sharing a package does not mean every rule is generated automatically.

A small example

Maya enters a capacity of -5. A browser check can help her notice the mistake immediately. If that check is bypassed, the backend schema still rejects the value. Separately, the backend checks whether Maya is allowed to perform the operation.

A DTO, or data transfer object, is simply the shape of data sent between parts of the program. An event DTO has separate date and time fields, while the database stores a date/time field. The repository converts between these shapes.

Generated tRPC types tell the frontend which operations and values are available. They do not copy the backend into the browser. SuperJSON helps requests and responses preserve values such as dates during conversion to transportable text.

06 / Backend

What the backend does with a request

NestJS organizes the backend into related groups of code. The application starts in main.ts, and app.module.ts connects its feature groups. Express provides the underlying HTTP request handling.

Inside a feature folder, names describe different responsibilities. Following those names helps you trace a request even before you understand the TypeScript syntax.

File role Plain-language job Example in this project
Router Receive a named operation and connect it to the work that handles it. The events router receives create, edit, delete, and detail requests.
Middleware Run a check around request handling. ProtectedMiddleware rejects a request without an authenticated session.
Service Coordinate the feature's behavior. The events service saves a new event, reads it back, and publishes a change message.
Repository Read or write stored records. The Drizzle events repository inserts an event into PostgreSQL.
Module Register the pieces and how they connect. EventsModule supplies the events router, service, and repository.

Dependency injection means that a piece of code receives the helpers it needs instead of constructing them itself. Nest connects the event service to a repository. Some feature modules can choose an in-memory repository for sample data instead of a database repository.

Such a concrete replacement is often called an adapter. It performs a known job using a particular tool or storage system. Not every feature currently has an in-memory adapter.

Two names that can be confusing

The events folder handles event creation, editing, and detail reads, but its tRPC name is eventCreation. The event-listings folder publishes the tRPC name events for lists and statistics. These are existing names; the guide uses them so you can find the code.

The word event also has two meanings. A calendar event is something people attend. A software event is a message that something happened, such as a user going online. The current EventsService contains both calendar-event behavior and generic message delivery.

07 / Database and cache

Where information is stored

PostgreSQL, also called Postgres, is the database. It stores records in tables. You can picture a table as rows and named columns: each event row has an ID, title, organizer, location, date/time, and other fields.

A primary key identifies a record. A foreign key refers to a record in another table. The organizer ID on an event refers to a user. These links let the database preserve relationships instead of relying on a copied user name.

Additional tables support authentication. accounts holds login-method information, including password hashes for password login. sessions records active sessions. Verification and two-factor tables support the related security workflows.

Drizzle and SQL

SQL is the language used to ask a relational database to read or change records. Drizzle is an ORM, an object-relational mapping tool. It lets this TypeScript application describe tables and construct database operations in code. PostgreSQL still stores the data and executes the resulting work.

Changing a table

A migration is a recorded change to database structure. Suppose a new feature needs an extra event field. A developer changes the shared table definition, generates a migration, reviews it, and applies it to the database. Editing a TypeScript definition alone does not alter an existing database.

This repository generates migrations with vp run db:generate. Developers must not manually edit the generated Drizzle migration SQL files. Seed data is sample data inserted to make local development useful before real users have created records.

There are two different caches

Storage Used for What to remember
PostgreSQL Durable users, events, and other records. Application restarts do not by themselves erase these records.
TanStack Query cache Frontend copies of recently fetched data. Pages use this to render and update. It is not the database.
Redis Backend cached results and rate-limit counters. Rate limiting means limiting how many requests a caller can make in a period.
Backend memory Presence connections and software-event delivery. This state belongs to the running process and is lost when it restarts.

08 / A complete example

Follow one event from form to database

Maya is ready to publish her board-game evening. Here is the full trip through this branch. Each step names the tool only after explaining the job.

  1. Maya opens the create-event page

    The route checks the session supplied by the root route. If no session is available, it sends her to the login page. This makes the interface helpful; the backend will check again.

  2. She fills in and submits the form

    EventForm collects the title, description, categories, location, address, date, time, image, and capacity. TanStack Query tracks the mutation, and the shared notification setup displays progress.

  3. The request reaches the backend

    The tRPC client sends the input to the backend and includes browser credentials. The backend resolves the session, rejects an anonymous request, and validates the submitted input.

  4. The backend assigns the organizer

    EventsRouter adds the authenticated user's ID. Maya does not supply an organizer ID in the event-creation payload. This prevents that field from choosing someone else as the owner.

  5. The database stores the event

    EventsService asks its repository to create the record. The Drizzle repository converts the input into the database shape and inserts it. PostgreSQL returns the new ID.

  6. The backend announces the stored change

    On this branch, the service reads the new record back, then emits an event-created message. Subscribers can receive the stored representation rather than an input that lacks the new ID.

  7. Maya sees the result

    The response contains the event ID. The frontend navigates to its detail page. Other subscribed event pages can refresh their lists after receiving the creation message.

Editing has another rule. For an update or deletion, the backend checks that the requester is the organizer or an administrator. A hidden button alone cannot enforce ownership.
Open the files in the same order
  1. create-event.tsx checks access to the page.
  2. EventForm.tsx collects input.
  3. events.router.ts handles the request.
  4. events.service.ts saves and announces the event.
  5. drizzle-events.repository.ts talks to storage.
  6. database.ts defines the table.
09 / Accounts

How login and permissions work

Authentication answers "Who are you?" Authorization answers "Are you allowed to do this?" A logged-in user has an identity, but does not automatically have permission to edit every event.

Better Auth implements account creation, login, sessions, and password-related workflows. Its requests go through /api/auth. Most other application data requests go through tRPC at /api/trpc. Login is therefore a separate route into the backend.

  1. Create an account

    The signup form calls Better Auth. For password login, the password is stored as a hash in the account records. A hash is a derived value used for verification, rather than a readable copy of the password.

  2. Log in

    Better Auth verifies the submitted credentials. A successful login establishes a session. The browser keeps a cookie, a small value it sends on later requests to help identify that session.

  3. Visit a protected page

    The frontend reads the session to present the right page and navigation. Backend request handling also resolves the session before protected operations.

  4. Check permission for an action

    An ordinary user can manage their own event. An administrator has broader permissions. The backend checks the role or ownership when it receives the request.

  5. Log out

    The frontend calls Better Auth to end the login session and refreshes the page's session information. Being logged out changes which actions are available.

Two-factor authentication, or 2FA, adds a verification step after the password. This project supports authenticator codes and backup codes. An authenticator code changes over time; backup codes provide another verification path.

Cookies must reach the backend from both the browser and server-rendered page requests. The project forwards incoming cookies when appropriate. CORS is the browser permission mechanism involved when the frontend and backend use different origins, such as different local ports. It is separate from user authorization.

Two account-creation paths currently exist

The real signup form uses Better Auth. The older admin-only users.createUser operation creates a user record without password credentials. That record alone cannot log in through the password form.

Password-reset code currently logs its reset link to the backend console. Welcome-email sending is connected to the legacy user-creation path, not to a Better Auth signup hook. These are current integration limits.

10 / Realtime and presence

How an open page hears about a change

A normal query ends when the server returns its answer. A subscription keeps a connection open for later messages. This branch uses Server-Sent Events, or SSE, through tRPC. The backend sends messages down that connection to the browser.

The useEventStream hook connects event messages to the frontend cache. A hook is reusable React code for state or other behavior. Creation messages trigger list refetches. Update and deletion messages patch existing list entries, and detail-cache entries are updated or removed.

A heartbeat is a periodic message saying the stream is still alive, even when no one is editing an event. The frontend watches for missed heartbeats. If the stream appears stale, it resets the subscription and refetches event lists.

This mechanism is process-local: the emitter delivers messages within one backend process. Redis does not distribute those messages across backend instances. Running several backend instances would require additional coordination. The stream also does not provide a permanent history of messages missed while disconnected.

Online status is a different kind of live data

Presence tracks active user connections in memory. One user can have multiple connections, such as several browser tabs. Removing one connection does not mark the user offline while another remains. When the last tracked connection closes, the user becomes offline.

When the backend is unavailable

On this branch, session loading returns no session when the authentication request fails, so public pages can still render as a visitor. Event listing routes allow their page to render when the initial data request fails. The interface can then show an error or connection state. This does not mean the database contents have disappeared.

12 / Code map

Find your way around the repository

A repository can mean the whole Git project, while a file named *.repository.ts means a data-access helper. Context tells you which meaning is intended. A monorepo is one repository containing multiple related applications or packages.

Location What you will find Start here when…
apps/frontend/src/routes Page definitions and initial data loading. You want to know which code owns a URL.
apps/frontend/src/components Forms, event cards, navigation, and other UI. You want to understand something visible on a page.
apps/frontend/src/hooks Reusable behavior such as subscriptions and presence. You want to understand live updates.
apps/frontend/src/integrations tRPC and query-cache setup. You want to follow requests out of the frontend.
apps/backend/src Feature folders plus authentication, configuration, and database setup. You want to understand a rule or backend operation.

apps/backend/drizzle Generated database migrations and metadata. You want to see how database structure changed.
docs Setup instructions, architecture explanations, and learning material. You need the project's documented workflow.
package.json and vite.config.ts Dependencies, commands, and task order. You want to understand what a development command runs.

Generated files

Some files are produced by tools. The tRPC router type, frontend route tree, and Paraglide runtime are examples. Edit the source definitions and run the generation task. Editing generated output directly can lose your changes the next time generation runs.

A package groups code with its dependencies and commands. A workspace is a package managed as part of this monorepo. @repo/schemas/events is an import name for shared event definitions, not a website address.

13 / From code to a running app

How developers run and change the project

A terminal accepts written commands. The project's development commands perform several tasks in a defined order. You do not have to start each application and generate each file by hand.

  1. Prepare the environment

    Follow the Development guide to use Nix or the Vite+ installation path. Install the dependencies. A dependency is another package the project needs.

  2. Start the development stack

    Run vp run dev, or bun dev in the documented Bun workflow. The task starts PostgreSQL and Redis, applies migrations, generates required code, and launches the frontend and backend.

  3. Open the website

    Visit http://localhost:3000 in a browser. Keep the terminal available because its logs explain failures that a page may only summarize.

  4. Change and check code

    During development, file watchers pick up changes. Developers also run formatting, type checks, and tests before treating the change as ready.

  5. Build and deploy

    A build prepares runnable application output. Deployment runs that output in its target environment. The project's local deployment command uses Docker Compose.

Command Purpose
vp run dev Start the normal local development stack.
vp run check Run the configured formatting, linting, and type checks.
vp run test Run the configured tests.
vp run build Prepare application build output.
vp run deploy Build and run the local Docker Compose deployment.

An environment variable is configuration supplied to a program, such as the backend address or database connection string. It lets the same code run in different environments. Secret configuration belongs outside published browser code and committed documentation.

A container is an isolated process environment with its required software. Docker Compose describes how several containers start and connect. A volume stores data outside a container's replaceable filesystem, so replacing a database container need not erase its records.

Linting checks code against rules. Formatting standardizes layout. Tests execute scenarios and compare results with expectations. CI, continuous integration, runs configured checks automatically when changes are submitted. Passing checks is useful evidence, but only for what those checks cover.

Use the normal development path first

Fixture mode is intended to use temporary sample data. On this branch, some module dependencies still require database configuration. Treat the no-database fixture path as incomplete rather than a guaranteed first-run shortcut. Use the normal setup instructions for onboarding.

14 / Terminology

A glossary you can return to

These definitions focus on the meanings used in this project. Expand any term for a short reminder.

API

The operations one program makes available to another. The frontend uses the backend's operations to read or change data.

Branch, commit, merge

A commit records a version of tracked files. A branch names a line of work. A merge combines histories. A branch can contain all of main and still have additional changes.

Cache and invalidation

A cache keeps a reusable copy. Invalidation marks a copy outdated so it can be refreshed. An event saved in PostgreSQL and a cached event in a browser can temporarily differ.

Client and server

A client requests work; a server answers. The browser is a client of the frontend server. The frontend server is itself a client when it requests backend data.

Component and hook

A React component describes part of the interface. A hook shares behavior or stateful logic between components.

CRUD

Create, read, update, and delete: the four common operations on stored records.

Database schema and validation schema

A database schema describes tables and columns. A validation schema describes which input or output values are acceptable. They are related definitions with different jobs.

DTO and serialization

A DTO is data arranged for transfer. Serialization converts a value into a form that can travel or be stored, such as text.

Error and status code

An error says an operation could not complete. HTTP status codes give categories, such as 401 for missing valid authentication, 403 for forbidden access, and 404 for something not found.

Frontend and backend

The frontend presents pages and interactions. The backend processes data requests and enforces permissions. Some frontend work happens on its own server.

Function, type, and state

A function is a named piece of work. A type describes expected values. State is information a program currently remembers, such as which dialog is open.

Hydration and SSR

SSR builds initial page HTML on the server. Hydration connects browser behavior to that HTML. The query cache can also be restored from the server's fetched data.

ID and relationship

An ID identifies a record. One record can store another record's ID to express a relationship, such as which user organized an event.

Middleware and dependency injection

Middleware runs around request handling. Dependency injection supplies a piece of code with its required helpers, such as a repository.

Migration and seed

A migration changes database structure. A seed supplies initial or sample records. A fixture is sample data used for development or tests.

Module and interface

A module groups related implementation behind a way to use it. That way to use it is its interface. In NestJS, a module also registers and connects application pieces.

Mutation, query, and subscription

A mutation changes data. A query reads it. A subscription keeps receiving later messages.

Route and router

A route connects a path or operation to code. The frontend router selects pages; a backend tRPC router groups data operations.

Session, cookie, and role

A session records a login. A cookie helps the browser identify that session on later requests. A role, such as admin, contributes to permission decisions.

Terminal, script, and build

The terminal accepts commands. A script is a reusable command sequence. A build prepares code and assets to run outside the development workflow.

15 / Continue learning

Where to go after this guide

You can now trace a user action through the system without needing to read every file. To build confidence, use these questions as checkpoints. The answers are hidden until you open them.

Why does the backend check input if the form already checks it?

Requests can come from outside our form. Browser checks help the user; backend checks protect the operation from invalid input.

Where does a saved event survive an application restart?

In PostgreSQL. A frontend cache and backend presence state are not the durable event record.

How does another browser learn that Maya edited an event?

The backend saves it and emits a change. An SSE subscription receives the message, the event-stream hook updates the cache, and React updates the display.

Does a user record always mean that person can log in?

No. The legacy user-creation operation does not create password credentials. The real signup path goes through Better Auth.

Can someone register for tickets just because the registrations table exists?

No. Storage is only one part of the feature. This branch still lacks the connected registration request handlers and full user flow.
