How splitLink chooses the transport

Read the subscription-versus-request decision, cookie forwarding, and SuperJSON together.

1. What transport means

Transport is how a request or message travels between the frontend and backend. tRPC gives you named operations and TypeScript types, but those operations still need a network mechanism. The splitLink configuration chooses that mechanism based on the operation kind.

Operation Link chosen Communication pattern
Query, such as users.getMe httpBatchLink HTTP request followed by a response
Mutation, such as friends.addFriend httpBatchLink HTTP request followed by a response
Subscription, such as presence.onPresenceChanged httpSubscriptionLink Server-Sent Events over an open HTTP connection

This code uses SSE, not a WebSocket connection. SSE carries messages from the server to the client. The browser makes ordinary HTTP requests for operations that change data. The split does not mean two backends: both branches use the same base tRPC URL.

2. Read the complete splitLink expression

splitLink({
  condition: (op) => op.type === 'subscription',
  true: httpSubscriptionLink({
    url: getUrl(),
    transformer: superjson,
    eventSourceOptions: { withCredentials: true },
  }),
  false: httpBatchLink({
    url: getUrl(),
    transformer: superjson,
    fetch: fetchWithCredentials,
    headers: () => (typeof window === 'undefined' ? getServerRequestHeaders() : {}),
  }),
})

A link is a processing step in the tRPC client. splitLink chooses one branch for each operation. It does not send every operation down both branches. In this object, true and false are property names accepted by splitLink, describing what to use when the condition returns true or false. 

condition: (op) => op.type === 'subscription'

This is an arrow function. op is the current operation object. The function reads its type and compares it to the exact string subscription using strict equality. It returns a boolean. The library calls this function; defining the callback does not run an API request by itself.

3. The subscription branch

httpSubscriptionLink connects subscription operations through SSE. A server-side async generator can yield one value, wait, and yield another. The tRPC integration carries these values through the connection to the frontend subscription callback. The link does not create the presence map or implement the event heartbeat; those belong to backend code.

eventSourceOptions: { withCredentials: true } configures credential handling for the SSE connection. This permits relevant browser credentials, such as cookies, subject to browser and server rules. It does not manufacture a session, override cookie restrictions, or make a public operation private.

A useful path to trace is Navbar or Profile → usePresenceConnection → presence.onPresenceChanged → the subscription branch → the presence generator. The generator checks ctx.user before tracking the connection. Public event subscriptions use the same transport but a different permission policy.

4. The query and mutation branch

httpBatchLink handles operations where the client asks for a result and receives a response. It can batch compatible operations into a request; that reduces transport overhead. Batching is not a database transaction and does not mean every operation in the batch must succeed or fail together. 

async function fetchWithCredentials(input: RequestInfo | URL, init?: RequestInit) {
  const response = await fetch(input, { ...init, credentials: 'include' });
  if (response.status === 413) {
    throw new Error(m.toast_request_too_large());
  }
  return response;
}

The wrapper forwards the supplied fetch options, then explicitly sets credentials to include. The spread copies the options; a later property with the same name wins. It also translates an HTTP 413 response, meaning the request body is too large, into a localized error. The m prefix refers to generated translation message helpers. This wrapper belongs to the batch branch; it is not the SSE eventSourceOptions setting.

5. Why browser and server rendering need different cookie handling

headers: () => (typeof window === 'undefined' ? getServerRequestHeaders() : {})

The ternary expression returns one value when its condition is true and another when false. The typeof check is safe even where window does not exist. In the frontend server-rendering process, it calls a server-only helper. In the browser, it supplies an empty extra-headers object. 

const getServerRequestHeaders = createServerOnlyFn(() => {
  const cookie = getRequestHeader('cookie');
  return cookie ? { cookie } : {};
});

During server rendering, the frontend server receives the visitor’s request. Its later request to the backend does not automatically inherit the visitor’s browser cookie. The helper reads the incoming Cookie header and forwards it. In the browser, credentialed fetch lets the browser handle cookies; the code does not manually read the Cookie header there.

Place where query runs How identity can reach the backend
Browser fetchWithCredentials uses credentials: include
Frontend server rendering The headers callback forwards the incoming cookie
Browser subscription EventSource uses withCredentials: true

Cookie settings, origin configuration, and backend session validation must still be correct. These options are necessary wiring, not authentication by themselves.

6. Both branches agree on data conversion

Both branches specify transformer: superjson. Network data must be serialized, meaning converted to a form that can be sent. SuperJSON preserves supported values such as JavaScript Dates with type information. The backend must use compatible transformation settings so the client can reconstruct the response.

This differs from Zod validation. A transformer describes how a value is transported; a schema checks whether the value is acceptable. Neither replaces permission checks.

7. Where the URL comes from

getUrl first tries VITE_API_URL. If it is null or undefined and the code is running on the server, it tries SERVER_URL. It then falls back to http://localhost:3001. It appends /api/trpc to the selected base. The nullish-coalescing operator ?? falls back for null or undefined; it does not treat every empty-looking value as missing. 

Browser query → selected base URL + /api/trpc → query handler
Browser stream → selected base URL + /api/trpc → subscription handler

The transport link adds the operation-specific request details. Changing between query and subscription does not mean inventing another base URL here.

8. The surrounding client and cache

createTRPCClient<AppRouter> creates the typed client. AppRouter describes available backend operations at TypeScript-checking time. The surrounding links array contains splitLink as its routing step. Later, createTRPCOptionsProxy connects this client to TanStack Query operation options.

The same file creates a QueryClient with a 30-second stale time and automatic query retries disabled by default. This matters when explaining outage recovery: an explicit invalidation or reconnect action is different from assuming this cache retries failed requests forever. The mutation cache in the rest of the file drives shared popup notifications, but it does not select the transport.

Questions to answer before reading the solutions

  1. Which branch handles friends.acceptFriend, and why?
  2. Does httpSubscriptionLink mean this project uses WebSockets for event updates?
  3. Why is credentials: include insufficient by itself for a backend request made during server rendering?
  4. Does batching two mutations make their database changes atomic?
  5. What is the difference between SuperJSON, Zod and a session check?

Answers and reasoning

  1. The false branch uses httpBatchLink because acceptFriend is a mutation, not a subscription. The condition checks the operation kind, not whether the name contains a particular word.
  2. No. The branch is configured for SSE over HTTP. The backend yields values and the client receives them over a stream.
  3. A server-side fetch has no automatic access to the visiting browser’s cookie jar. The server-only helper explicitly forwards the Cookie header from the incoming request.
  4. No. A transport batch groups operations for sending. Database atomicity requires appropriate transaction logic in the backend.
  5. SuperJSON serializes and restores values. Zod validates their shape or rules. A session check identifies whether the request has an authenticated user. They solve different problems.
