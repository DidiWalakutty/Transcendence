PresenceService and its connection map

A complete explanation of the small service, including the nested generic type and multi-connection behavior.

1. What online means in this implementation

PresenceService records active tracked connections in one backend process. A user is considered online if that process has at least one connection ID for them. It does not store a permanent online flag in PostgreSQL, measure whether the person is watching the screen, or query Redis.

The router tells this service when a subscription begins and ends. The service changes its collection and reports whether the user crossed between online and offline. A separate class sends presence messages.

2. Imports, decorator and class property

import { randomUUID } from 'node:crypto';
import { Injectable } from '@nestjs/common';

@Injectable()
export class PresenceService {
  private readonly connections = new Map<string, Set<string>>();
}

randomUUID generates a fresh identifier for a connection. Injectable lets Nest manage the service as a dependency. export allows other files to import it. The private property is internal to the service. readonly prevents replacing the map reference after initialization; it does not prevent changing map entries.

3. Read Map<string, Set<string>> from the inside out

A Set holds unique values. Here those values are connection-ID strings. A Map associates keys with values. Here the key is a user-ID string, and its value is a Set of connection-ID strings. The angle brackets are generic type arguments telling TypeScript what belongs in the collection. 

// A conceptual picture, not a JSON encoding of Map and Set:
user-A → Set { connection-1, connection-2 }
user-B → Set { connection-3 }
Expression Meaning
connections.get(userId) Get that user’s Set, or undefined if absent
connections.set(userId, set) Associate the user with a Set
connections.has(userId) Check whether the map contains this user
connections.delete(userId) Remove the user entry
aSet.add(connectionId) Add one connection ID
aSet.delete(connectionId) Remove one connection ID
aSet.size Count the remaining IDs

The invariant, meaning the rule the methods keep true, is that each stored user has a nonempty connection set. An empty set is removed. That is why checking map membership is enough to decide who is online.

4. Why a Set of users or one boolean would be insufficient

Suppose Maya has two tracked connections. If the server stored only Maya → true, closing one connection could incorrectly set Maya → false even while the second remained active. A connection set lets the server remove exactly the connection that ended.

A counter could track a total, but storing unique connection IDs makes repeated disconnect handling safer: deleting an ID that is already absent does not decrement a counter below its correct value. One browser tab can also have more than one subscription; this design counts connections, not assumed tabs.

5. connect adds one connection and reports a transition

connect(userId: string): { connectionId: string; wasOffline: boolean } {
  const connectionId = randomUUID();
  const connections = this.connections.get(userId);
  // ...
}

The method is synchronous: it does not await a database or network request. The return annotation describes an object with the new connection ID and a boolean. The local variable named connections is the user’s Set. this.connections is the Map for all users. Distinguishing those two names prevents confusion.

If the map has no entry, the local value is undefined and if (!connections) is true. The method creates a Set containing the new ID, stores it, and returns wasOffline: true. This means the user was offline before this call and is online now.

If an entry exists, connections.add(connectionId) mutates that stored Set. It need not call map.set again because get returned the same Set object held by the map. It returns wasOffline: false because the user already had an active connection.

wasOffline: false does not mean the user is offline now. Both successful connect branches leave the user online. The flag tells the caller whether it needs to announce an offline-to-online transition.

6. disconnect removes one connection

disconnect accepts a user ID and the particular connection ID. It gets that user’s Set. If the user entry is absent, it returns becameOffline: false, because this call did not cause an online-to-offline transition. 

connections.delete(connectionId);
if (connections.size === 0) {
  this.connections.delete(userId);
  return { becameOffline: true };
}
return { becameOffline: false };

Deleting one ID can leave others active. Only when the Set becomes empty does it remove the map entry and return true. The returned boolean describes what changed, not simply the final online state. An unknown user is offline, but disconnecting that unknown user still returns false because nothing changed.

7. Trace two connections by hand

Action Stored connections for A Return flag A online afterwards?
connect(A) {c1} wasOffline: true Yes
connect(A) {c1, c2} wasOffline: false Yes
disconnect(A, c1) {c2} becameOffline: false Yes
disconnect(A, c1) again {c2} becameOffline: false Yes
disconnect(A, c2) No map entry becameOffline: true No
disconnect(A, c2) again No map entry becameOffline: false No

c1 and c2 are short teaching labels. The implementation returns UUID strings. No timer automatically expires these entries inside PresenceService. Correct cleanup in the router is therefore part of correctness, not optional housekeeping.

8. getOnlineUserIds filters a requested list

getOnlineUserIds(userIds: string[]): string[] {
  return userIds.filter((userId) => this.connections.has(userId));
}

The input and output are arrays of strings. filter keeps IDs for which map.has returns true. The callback does not create connections or announce changes. It asks about the present state. 

// If only user-A is online:
getOnlineUserIds(['user-A', 'user-B'])
// returns ['user-A']

The method preserves input order and does not remove duplicate input IDs. It returns only the requested online users, not a dump of every map entry. Authentication and UUID validation are the router’s responsibility.

9. Lifetimes and existing tests

A backend process restart loses this map. Separate backend instances have separate maps unless a shared presence mechanism is added. A singleton service in one process lets its routers see the same connections, but does not make that state global across machines.

The existing service tests cover the first connection, multiple connections, the last disconnect, repeated or unknown disconnects, and filtering requested users. They establish local collection behavior. They do not establish that every network-disconnection path triggers router cleanup.

Questions to answer before reading the solutions

  1. What are the key and value types in the map?
  2. Why does the second connect return wasOffline: false even though the user is online?
  3. Why does calling Set.add after Map.get change the stored state?
  4. What happens when one of two connections disconnects?
  5. Why can an unknown-user disconnect return becameOffline: false?
  6. What happens to online state after a backend restart?

Answers and reasoning

  1. The key is a user-ID string. The value is a Set of connection-ID strings. Each user can have several independently removable connections.
  2. The flag describes the state before this connect call. The user was already online, so this call did not cause a new online transition.
  3. The Set is an object. Map.get returns the stored object reference, not a cloned Set. Adding to it changes the same Set the map holds.
  4. Only that connection ID is removed. The remaining connection keeps the user online.
  5. No online-to-offline transition occurred. The user was not tracked before the call.
  6. The in-memory map disappears. New subscriptions need to register connections again.
