Friends: router, service, repository and schemas

A complete request-to-database walkthrough of friendship creation, acceptance, listing and removal.

1. Follow the feature through its layers

The friends feature connects a user action to a stored relationship. The router exposes operations and checks login. The service coordinates rules such as rejecting self-requests. The Drizzle repository performs database queries. The database schema defines stored columns, and friends.ts defines runtime request/response schemas and TypeScript DTO types. 

Profile sends friendId
  → FriendsRouter takes myId from ctx.user.id
  → FriendsService checks applicable rules
  → DrizzleFriendsRepository reads or changes rows
  → router returns users or a friendship record

Maya and Leo are teaching names below. A and B are shortened symbolic IDs, not values that would pass the actual UUID validators.

2. Read the stored relationship first

export const friendshipStatus = pgEnum('friendship_status', ['pending', 'accepted']);

export const friends = pgTable('friends', {
  myId: uuid('my_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  friendId: uuid('friend_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  status: friendshipStatus('f_status').notNull().default('pending'),
  createdAt: timestamp('created_at').notNull().defaultNow(),
});

pgTable describes a PostgreSQL table through Drizzle. The JavaScript property names myId and friendId map to SQL column names my_id and friend_id. uuid specifies the column type. notNull requires a value. references creates a foreign-key relationship to a users row. onDelete: cascade means deleting a referenced user also deletes related friendship rows.

The enum restricts status to pending or accepted. The default supplies pending when an insert omits status. defaultNow supplies the creation timestamp. These database defaults do not mean a request can ignore every API requirement; storage and request validation are separate layers.

Column Meaning for Maya requesting Leo
myId Maya, the original sender
friendId Leo, the original recipient
status pending before acceptance, accepted afterwards
createdAt When this row was created

Acceptance changes status; it does not swap the two IDs or create a reverse row. The relationship is stored once with its original direction. Reading accepted friends must therefore work from either side. The shown table has no separate friendship ID, primary key, unique pair constraint, or database self-friend check. Those absences matter when reasoning about concurrency and duplicate rows.

3. What packages/schemas/src/friends.ts exports

export const friendSchema = createSelectSchema(friends, {
  createdAt: () => z.coerce.date(),
});

createSelectSchema derives a runtime Zod schema from the Drizzle table. It describes a selected friendship row, not a user profile. The createdAt override coerces supported date input into a JavaScript Date before validation completes, which is useful when a date arrived as serialized text. 

export const addFriendSchema = z.object({ friendId: z.uuid() });
export const removeFriendSchema = z.object({ friendId: z.uuid() });

These inputs accept the other person’s ID. They do not accept the acting user’s ID. That identity comes from authenticated context in the router. The add and remove input shapes happen to be the same, but their exported names express their intended operations.

respondFriendSchema also exists with myId, friendId and accept fields. However, the inspected router does not use it. acceptFriend uses addFriendSchema. Do not infer a working reject-by-boolean endpoint merely because a schema defines an accept field. 

export type AddFriendDto = z.infer<typeof addFriendSchema>;

typeof here refers to the schema’s TypeScript type. z.infer extracts the TypeScript value shape accepted by that schema. The exported DTO is a compile-time type; the schema is the runtime validation object. FriendDto, RespondFriendDto, and RemoveFriendDto follow the same pattern.

4. FriendsRouter receives requests

@Router({ alias: 'friends' }) makes the frontend names friends.getFriends, friends.addFriend and so on. The constructor receives FriendsService through dependency injection. @Query and @Mutation identify the operation kind and configure schemas. @Input supplies parsed submitted values, and @Ctx supplies request context.

Every method explicitly checks if (!ctx.user) and throws UNAUTHORIZED if needed. This router does not use ProtectedMiddleware for these checks. After the guard, ctx.user.id is the acting user. Direct method calls in tests do not automatically reproduce all framework schema parsing, but the explicit guard remains ordinary method code.

Router method Input from caller Service arguments Successful output
getFriends None Current user ID User objects for accepted friends
getPendingRequests None Current user ID User objects for incoming senders
addFriend friendId Current user ID, other ID Friendship row
acceptFriend friendId, using addFriendSchema Current recipient ID, sender ID Friendship row
removeFriend friendId Current user ID, other ID Removed friendship row

The two query output schemas are userSchema.array(), because the UI needs people to display. Mutation output is friendSchema, because those methods return the relationship row. Confusing user data and relationship data makes the result types harder to understand.

5. How the router represents failure

addFriend returns the service result directly. Self or duplicate errors thrown by the service propagate through the request. acceptFriend and removeFriend also inspect the result. If the repository changed no matching row, the returned first row is undefined, so the router throws NOT_FOUND. 

const friendship = await this.friendsService.acceptFriend(ctx.user.id, input.friendId);
if (!friendship) throw notFoundError('Friend request not found');
return friendship;

Throwing is an unsuccessful operation. Returning undefined or false normally would not express the same error contract to a mutation caller. The context-based ID is also a permission boundary: another user cannot choose to act as Maya merely by sending a myId field.

6. FriendsService coordinates the rules

Injectable lets Nest manage the service. The injected FriendsRepository is an abstract contract, meaning the service depends on available operations rather than a particular SQL implementation. The read, accept, and remove methods currently delegate straight to repository methods. 

async addFriend(myId: string, friendId: string) {
  if (myId === friendId) {
    throw conflictError('You cannot add yourself as a friend');
  }
  const existing = await this.repository.findFriendship(myId, friendId);
  if (existing) {
    throw conflictError('Friend request already exists');
  }
  return this.repository.addFriend(myId, friendId);
}

Strict equality rejects self-requests. The awaited lookup checks whether any relationship already exists in either direction. It does not only check accepted friends: an existing pending request also causes a conflict. If neither condition blocks the operation, the repository inserts a pending row.

This service does not explicitly check whether the target user exists. The foreign key supplies a database constraint for that. It also does not place the duplicate lookup and insert inside a transaction or enforce pair uniqueness. Two concurrent requests can both pass the lookup. A source-based explanation should not claim that this check alone guarantees no duplicates.

7. The repository class, inheritance and injected database

export class DrizzleFriendsRepository extends FriendsRepository {
  constructor(@Inject(DATABASE) private readonly db: Database) {
    super();
  }
}

extends says this class implements the inherited repository contract. super() calls the parent constructor, as required before using this in a derived class constructor. @Inject(DATABASE) tells Nest which registered provider to supply. Database is a TypeScript type describing the database object; the DATABASE token is the runtime lookup identifier.

The imported eq, and and or functions build SQL conditions. They are not in-memory JavaScript filters. Drizzle translates the chained query into database operations using the table definitions.

8. findFriends joins either side to the other user

The query starts from friends rows and joins users. An inner join pairs rows only when its condition matches. The condition covers two possibilities: the current user is the sender, or the current user is the recipient. 

or(
  and(eq(friends.myId, userId), eq(users.id, friends.friendId)),
  and(eq(friends.friendId, userId), eq(users.id, friends.myId)),
)
  1. If userId is the row’s myId, join the users row whose ID equals friendId.
  2. If userId is the row’s friendId, join the users row whose ID equals myId.
  3. Keep only friendship rows whose status is accepted.

For the stored row A → B, asking as A returns B’s user record, while asking as B returns A’s user record. This is why the query does not simply join users.id to friendId in every case. 

return rows.map((row) => row.user);

select({ user: users }) gives rows shaped like { user: ... }. map removes that wrapper and returns an array of user records. It does not change the database. The query does not specify an ordering or deduplicate repeated relationship rows.

9. findPendingRequests returns incoming requests

.innerJoin(users, eq(users.id, friends.myId))
.where(and(eq(friends.friendId, userId), eq(friends.status, 'pending')))

Here direction is intentional. The requested user must be the recipient. The joined user is the sender. If Maya sent Leo a pending request, Leo sees Maya in this result. Maya does not see her own outgoing request in this query. An outgoing-request screen would require another query or different filtering.

10. addFriend inserts, then returns the row

const [friendship] = await this.db
  .insert(friends)
  .values({ myId, friendId, status: 'pending' })
  .returning();
return friendship;

insert chooses the table. values supplies the row values; shorthand myId means myId: myId. returning asks PostgreSQL for the inserted row data. The result is an array, so const [friendship] uses array destructuring to take its first element. The operation inserts one row in this method.

11. findFriendship checks the pair in both directions

findFirst searches for either myId=A and friendId=B, or myId=B and friendId=A. This detects an existing request regardless of who originally sent it. There is no status filter, so accepted and pending rows both count. findFirst returns one match or undefined; it does not establish that the database cannot hold additional matches.

12. acceptFriend deliberately reverses the parameter comparisons

.update(friends)
.set({ status: 'accepted' })
.where(and(eq(friends.myId, friendId), eq(friends.friendId, myId)))
.returning()

In this method’s parameters, myId is the current actor. In the stored row, myId is the original sender. Those are different roles during acceptance. For Maya=A sending to Leo=B, Leo calls with myId=B and friendId=A. The filter looks for stored sender A and stored recipient B, then changes status to accepted.

Expression For Leo accepting Maya
Method argument myId B, current logged-in recipient
Method argument friendId A, original sender
Stored friends.myId must equal A, the friendId argument
Stored friends.friendId must equal B, the myId argument

This direction check prevents the original sender from accepting their own outgoing request through this method. A third user cannot match the recipient field with their authenticated ID.

The current acceptance WHERE clause does not require status=pending. Reaccepting an already accepted matching row can succeed. Also, SQL update can affect every matching duplicate row, while destructuring returns only the first one. These are properties of the existing implementation, not extra guarantees implied by the method name.

13. removeFriend removes either direction

Removal checks both directions, like findFriendship. This lets either party remove their relationship. It has no status filter, so it can also remove a pending row if the API is called for one. The existing page may expose fewer actions than the API can perform. The database deletes matching rows and returning supplies their former values; the method returns the first.

The service does not first look up the relationship here. An absent match leads to undefined, which the router turns into NOT_FOUND. The authenticated user ID is part of both allowed pair comparisons, so arbitrary unrelated rows do not match.

14. One complete friendship lifecycle

Action Stored row afterwards Visible result
Maya adds Leo A → B, pending Leo can query Maya as an incoming request
Leo accepts Maya A → B, accepted Both accepted-friends queries return the other person
Maya removes Leo No matching row Neither sees this accepted friendship afterwards

In the profile UI, successful mutations invalidate relevant query-cache entries. This refreshes the current browser’s saved responses. The friends methods shown here do not broadcast a friend-list-change event. Presence messages update online status and should not be confused with notifications that a friendship row changed.

15. What to be ready to explain

  • Why the backend obtains the acting user from context instead of trusting submitted myId.
  • Why pending request direction matters, but accepted-friend lookup must handle both directions.
  • Why read operations return users while mutations return friendship records.
  • Why the service’s duplicate lookup is useful but weaker than a database uniqueness guarantee.
  • Why a DTO type, a Zod schema, and a foreign key each enforce a different kind of rule.
  • Why respondFriendSchema is not evidence that a corresponding endpoint is wired up.

Questions to answer before reading the solutions

  1. For Maya sending Leo a request, which ID is stored in myId and which in friendId?
  2. Why does accepted-friend lookup need two branches but incoming-request lookup does not?
  3. When Leo accepts Maya, why is friends.myId compared with the method’s friendId argument?
  4. Which layer rejects self-requests? Which checks login? Which enforces referenced users exist?
  5. Can two simultaneous add requests pass the current duplicate check?
  6. Does acceptFriend require a pending status in its SQL condition?
  7. What does const [friendship] extract, and what if there are no returned rows?
  8. Does respondFriendSchema define the input actually used by acceptFriend?

Answers and reasoning

  1. The stored myId is Maya, the sender. The stored friendId is Leo, the recipient. Acceptance preserves that orientation.
  2. Accepted friendship should be visible to both sides of the same row. Incoming requests intentionally select only rows addressed to the current user and return the sender.
  3. The method’s myId is the actor Leo. The table’s myId is the original sender Maya. The friendId argument names Maya, so that is the correct sender comparison.
  4. The service rejects self-requests. The router explicitly checks ctx.user. PostgreSQL foreign keys require referenced user records, though the service does not provide a separate friendly target-exists check.
  5. Yes, the read-then-insert sequence alone does not prevent both requests finding no row before either inserts. The shown table lacks a unique pair constraint.
  6. No. It filters by sender and recipient only and sets status to accepted. Repeating acceptance on an already accepted row is not rejected solely by that WHERE clause.
  7. It takes the first element of the array returned by returning(). With no rows, it is undefined. The accept and remove router handlers turn that into a not-found error.
  8. No. The router uses addFriendSchema for acceptance. respondFriendSchema is defined but not used by the inspected app operations.
