The presence generator and resource cleanup

A full explanation of the initial yield, later messages, cancellation signal, and finally block.

1. The router exposes a snapshot and a stream

PresenceRouter offers two operations under the tRPC alias presence. getOnlineUserIds answers a current-state question once. onPresenceChanged starts a tracked connection and yields later status messages. Both explicitly check for ctx.user. The class receives PresenceService for connection bookkeeping and PresenceEvents for publishing and listening.

Operation Input Output Side effect
getOnlineUserIds An array of user IDs The requested IDs that are online None in PresenceService
onPresenceChanged No application input; context and options supplied by framework userId and online status messages Registers a tracked connection for the subscriber

2. Decorators, types and request context

@Router({ alias: 'presence' }) groups these operations. @Query registers the snapshot query and its schemas. @Subscription registers the stream. @Input() supplies parsed request input, @Ctx() supplies backend context, and @Options() supplies operation options such as the AbortSignal. Type annotations describe expectations to TypeScript; decorators and runtime checks connect them to actual requests.

The context type allows user to be null. if (!ctx.user) throw unauthorizedError(...) rejects an anonymous call. After that guard, code can use ctx.user.id. The snapshot schema checks an array of UUIDs, and the service filters those IDs against its map.

The subscription output helper expresses an asynchronous stream type. It is defined with z.custom and no predicate, so it should not be described as deep runtime validation of every emitted field.

3. Read the generator signature

async *onPresenceChanged(
  @Ctx() ctx: { user: { id: string } | null },
  @Options() opts: { signal?: AbortSignal },
): AsyncGenerator<PresenceChangedDto, void, void>

async allows waiting for asynchronous results. The asterisk makes it a generator, which can produce multiple values with yield. AsyncGenerator’s first type parameter is the yielded value type. The other two void parameters mean no useful final return value and no useful input values sent back into the generator.

Creating a generator does not execute its full body immediately. A consumer requests its next value through next() or a for-await loop. Execution can stop temporarily at a yield and continue when the consumer asks for more.

The signal is optional. An AbortSignal lets the framework communicate cancellation to the underlying listener. It is not a timeout value, a promise, or a user ID.

4. Register the connection before streaming

const userId = ctx.user.id;
const { connectionId, wasOffline } = this.presenceService.connect(userId);

The server gets identity from authenticated context. The client does not choose which user to mark online through an input payload. Object destructuring extracts connectionId and wasOffline from the returned object, equivalent to storing the result and reading those two properties.

The connection ID identifies this subscription’s bookkeeping entry. It must be remembered so cleanup removes this entry rather than all connections for the user. wasOffline identifies whether this is the user’s first active tracked connection.

5. Broadcast the first online transition

if (wasOffline) {
  this.presenceEvents.emitPresenceChanged({ userId, online: true });
}

Only the first connection publishes the online transition to existing listeners. A second connection leaves the user online, so no state transition needs broadcasting. PresenceEvents is a small wrapper around EventsService’s generic emitter and listener with the channel name presence.changed. The presence map and emitter are both local to this backend process.

6. Why the direct yield is necessary

yield { userId, online: true };

The broadcast above occurs before this new generator reaches its listening loop. The underlying listener registers only when it starts being consumed. The new subscriber therefore cannot rely on receiving its own earlier broadcast. The direct yield sends an initial online message to this subscriber itself.

Sequence What happens
1 The generator registers this connection in PresenceService.
2 If this is the first connection, it broadcasts online to existing listeners.
3 It yields an online message directly to the connecting consumer.
4 When the consumer asks for the next value, it enters the loop that listens for future changes.

A snapshot query can also have run before the subscription registered the connection. That explains the original symptom of appearing offline immediately after login. The direct yield supplies an initial message, while the frontend’s own-status display also follows the subscription connection state.

The direct yield is for this consumer; it is not another broadcast. It runs even for a second connection when wasOffline is false. It fixes this particular self-online ordering problem. It does not make all snapshot and subscription startup sequences globally atomic or replay messages sent before listening began.

7. Forward later presence messages

for await (const change of this.presenceEvents.listenPresenceChanged(opts.signal)) {
  yield change;
}

The for-await loop requests messages from an asynchronous iterable. Whenever the internal listener produces a change, the router yields it outward to tRPC. This is delegation: the router does not implement the queue or wake-up function itself. The generic EventsService listener does that work.

PresenceChangedDto contains a userId and an online boolean. The stream can carry changes for users other than the subscriber. The snapshot query filters requested IDs, but this stream does not apply a friends-only filter. Authentication is required to subscribe; the current implementation is not a separate per-friend stream.

This presence stream calls listenPresenceChanged, which uses the generic listener. It does not call the calendar-event heartbeat wrapper. Do not assume that every tRPC subscription inherits the heartbeat behavior of useEventStream.

8. What finally owns and closes

finally {
  const { becameOffline } = this.presenceService.disconnect(userId, connectionId);
  if (becameOffline) {
    this.presenceEvents.emitPresenceChanged({ userId, online: false });
  }
}

When control leaves the entered try block, finally removes the connection this generator registered. If other connections remain for the user, becameOffline is false and no offline transition is broadcast. If this was the last connection, it announces offline.

For a normal framework cancellation after the loop has started, the signal wakes the underlying waiting listener. That listener exits and removes its event-emitter and abort callbacks. The outer generator then removes its presence connection. Each layer has its own cleanup job.

Owner in this path Resource it opens Cleanup
PresenceRouter generator PresenceService connection ID disconnect(userId, connectionId)
EventsService.listen Emitter callback and abort callback off() and removeEventListener() in its finally
Calendar-event heartbeat wrapper, in a different path Heartbeat timer clearTimeout() in that wrapper

docs/API.md states: "whoever opens a resource closes it." In this path the router opens the presence registration, so its finally owns that registration. The lower-level listener cannot infer which presence connection to remove just because it knows a channel name. A service-level abstraction could own the whole lifecycle in a refactor, but that is not how this file is currently arranged.

9. Read the placement of try carefully

There is a real boundary in the current code: connect() and the first direct yield happen before the try block. If a consumer asks the generator to return while it is suspended at that first yield, the later try/finally has not been entered and will not clean up that registration. Likewise, an exception before entering try is outside its protection. Therefore "finally always cleans up this connection" is too broad. A lifecycle-safe arrangement would place the work after a successful connect, including the first yield, inside the protected try/finally. This lesson documents the source; it does not change it.

This is a useful distinction between understanding intended cleanup and verifying every exit path. Existing PresenceService tests exercise the map, not this generator’s early-return path. Closing a network connection, setting an abort signal, and calling a generator’s return method are related lifecycle operations, but they are not interchangeable automatic guarantees.

10. Follow a multi-connection disconnect

Maya has connection c1 in one subscription and c2 in another. When c1’s entered loop exits, its finally removes only c1. The map still holds c2, so no offline event is emitted. When c2 later exits and is removed, the map has no Maya entry, and the router broadcasts offline. This is why the return flags from PresenceService describe transitions rather than simply current state.

Questions to answer before reading the solutions

  1. Why does the connecting client need a direct yield after an online broadcast?
  2. Does the second connection receive an initial online message? Does it broadcast another online transition?
  3. Who removes the emitter listener, and who removes the presence connection?
  4. Does the presence stream automatically have the calendar-event heartbeat?
  5. Why is a first yield before try a cleanup concern?
  6. If one of two active connections closes normally, should the router announce offline?

Answers and reasoning

  1. Its listener has not started consuming when the earlier broadcast occurs. Existing listeners can receive that broadcast, but the connecting client gets its initial status from the direct yield.
  2. Yes, the direct yield is unconditional after login and connect. No, the transition broadcast only runs when wasOffline is true.
  3. EventsService.listen removes its emitter and abort callbacks. This router removes the connection ID it opened through PresenceService. The generic listener has no ownership of that presence registration.
  4. No. PresenceEvents uses the generic listener. The heartbeat wrapper belongs to the calendar-event stream and is not called here.
  5. The generator can be suspended before entering try. Returning at that point does not execute the later finally. Resource protection should cover the first yield after acquiring a connection.
  6. No. Removing one connection leaves another in the Set. Only removal of the last connection produces becameOffline: true.
